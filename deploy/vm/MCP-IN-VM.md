# The hosted MCP server inside the VM — measure first, then decide (story 4804)

Status: **AC1 and a design paragraph only.** Nothing here changes any service. It is the order of work for story 4804 (INFRA-DIET ⑪): the Cloud Run service `sprintable-mcp-prod` is the largest single item left after the prod move and the removals (about 59 USD a month at the product owner's count: 2,601,864 s × (2.16e-5 per vCPU-s + 0.5 GiB × 2.4e-6)), and the VM's stack has no MCP in it. **Nothing goes to `main` until the prod move and one day after it are over** (the rule of step 4c to step 8 of [CUTOVER-prod.md](CUTOVER-prod.md) goes on to the day after); everything is done on `develop` and the dev VM first. The agent has no cloud access: it writes the lines, the product owner runs them and writes the numbers into the places marked **MEASURE**. A number nobody has measured is written «unmeasured», never guessed.

## 1. What the repository says about the MCP server (so the measurements ask the right question)

| Fact | Where |
|---|---|
| The hosted server is **stateless Streamable HTTP** (`stateless_http=True`): no session is kept between requests; every request carries its own bearer key (the agent's API key) and that key is the authentication. A fallback key can be configured (`AGENT_API_KEY`; the prod script of Cloud Run injects one from Secret Manager); it is never used while a request has a bearer, and without it the code falls back to a constant placeholder. | `backend/sprintable_mcp/__main__.py` `_run_http` |
| In the HTTP mode **the event bridge is not started** (it belongs to the stdio mode of the lane agents). The HTTP server is tools only. | same, docstring of `_run_http` |
| It listens on `$PORT` (else 8080), path `/mcp`, and refuses a `Host` that is not in `MCP_ALLOWED_HOSTS` (exact names) when that variable is set. | `config.py`, `server.py` (`transport_security`) |
| It is **the backend's own image** started with another command (`python -m sprintable_mcp`, `MCP_TRANSPORT=http`): no image of its own to build. | `backend/scripts/deploy_mcp_prod.sh`, `deploy_mcp_dev.sh` |
| It calls the backend over HTTP at `SPRINTABLE_API_URL` and keeps small caches (`mcp_scope_cache_max_size` 1000 keys); a request body can be as large as 16 MiB (attachments). | `config.py`, `server.py` |
| On Cloud Run it is deployed with `--min-instances=0 --max-instances=2`; the product owner reads **CPU throttling off** (instance-based billing) and about 0.99 billed instances over the last 24 hours. | `deploy_mcp_prod.sh`; product owner's reading |
| The customer-facing name is `mcp.sprintable.ai` (dev: `dev-mcp.sprintable.ai`), a Cloudflare name in front of the `run.app` address; `MCP_ALLOWED_HOSTS` lists both the `run.app` host and `mcp.sprintable.ai`. | `deploy_mcp_prod.sh`, [RUNBOOK §8](RUNBOOK.md) (the `dev-mcp` row of the DNS table) |

**The question the numbers must answer first: why is one instance billed all day?** Cloud Run keeps an instance for about 15 minutes after its last request, and with CPU throttling off it bills the instance for all of that time. The server is stateless, so its requests should be short; if requests come more often than every 15 minutes, round the clock, one instance is billed round the clock **without any long connection at all**. That is a different problem from «a stream is held open», and it has a different and much cheaper answer (below, case A). Only the request log of the service can tell the two apart.

## 2. AC1 — the measurements (read-only; the product owner runs them)

`PROJECT=sprintable-494803`, `REGION=asia-northeast3`; the MCP services are `sprintable-mcp-prod` and `sprintable-mcp-dev`; the VMs are `sprintable-vm-dev` and (after the window) `sprintable-vm-prod`.

**2a. The traffic of `sprintable-mcp-prod`, 7 days: how many requests, how long each lasts, who sends them.** (The platform's request log; paths and methods only, never a key.)

```
SVC=sprintable-mcp-prod
gcloud logging read "resource.type=\"cloud_run_revision\" AND resource.labels.service_name=\"${SVC}\"" --project $PROJECT --freshness=7d --limit=100000 --format='value(timestamp)' | cut -c1-10 | sort | uniq -c
gcloud logging read "resource.type=\"cloud_run_revision\" AND resource.labels.service_name=\"${SVC}\" AND httpRequest.requestMethod=\"GET\" AND httpRequest.latency>\"30s\"" --project $PROJECT --freshness=7d --limit=100000 --format='value(timestamp)' | cut -c1-10 | sort | uniq -c
gcloud logging read "resource.type=\"cloud_run_revision\" AND resource.labels.service_name=\"${SVC}\" AND httpRequest.requestMethod=\"POST\" AND httpRequest.latency>\"30s\"" --project $PROJECT --freshness=7d --limit=100000 --format='value(timestamp)' | cut -c1-10 | sort | uniq -c
gcloud logging read "resource.type=\"cloud_run_revision\" AND resource.labels.service_name=\"${SVC}\"" --project $PROJECT --freshness=7d --limit=100000 --format='value(httpRequest.requestMethod,httpRequest.status)' | sort | uniq -c | sort -rn | head -12
gcloud logging read "resource.type=\"cloud_run_revision\" AND resource.labels.service_name=\"${SVC}\"" --project $PROJECT --freshness=7d --limit=100000 --format='value(httpRequest.userAgent)' | sort | uniq -c | sort -rn | head -10
gcloud logging read "resource.type=\"cloud_run_revision\" AND resource.labels.service_name=\"${SVC}\" AND httpRequest.latency>\"30s\"" --project $PROJECT --freshness=7d --limit=100000 --format='value(httpRequest.latency)' | sed 's/s$//' | awk '{t += $1; n++} END {printf "%d requests over 30 s, %.0f s, %.3f concurrent on average (7 days)\n", n, t, t / 604800}'
gcloud logging read "resource.type=\"cloud_run_revision\" AND resource.labels.service_name=\"${SVC}\"" --project $PROJECT --freshness=1d --limit=1000000 --format='value(httpRequest.latency)' | sed 's/s$//' | awk '{t += $1; n++} END {printf "%d requests, %.0f s, %.3f concurrent on average (24 hours)\n", n, t, t / 86400}'
```

The first line is requests per day; the second and the third are the `GET` and the `POST` requests that lasted more than 30 seconds, per day (**a stateless server should have none of the first**: a `GET` that lasts is a stream held open; a `POST` that lasts may be a slow tool call that waits for the backend **or** an answer that is itself a stream — Streamable HTTP allows both, and the latency does not say which, so both are counted and **both count as held time**); the fourth is the methods and answers (a `GET` that answers 405 or 200, a `POST` that answers 200, a 401 for a key that is dead); the fifth is who sends them (user agents, no addresses); the sixth and the seventh are **the time itself**: the latencies of the requests over 30 seconds (7 days) and of **all** requests (the last 24 hours, up to a million), each added up and divided by the seconds of its period — the average number of requests being served at the same moment. It is an upper bound of the share of one instance that is busy: two requests that overlap on one instance are counted twice, so a figure below 0.1 is certain to be below 0.1 of an instance, and a figure above it is not yet a held connection. A count of 100000 (1000000 for the last line) means «at least»: read a shorter `--freshness`. **MEASURE:** requests a day, `GET` over 30 s a day, `POST` over 30 s a day, the five biggest user agents, and the two averages of concurrent requests.

**2b. The instance and its memory, from Monitoring (7 days, hourly; read-only).** The metrics are Cloud Run's own: `run.googleapis.com/container/billable_instance_time` (seconds billed per second: the 0.99), `container/instance_count` (by `state`: active or idle), `container/memory/utilizations` (the 99th percentile and the maximum), `container/max_request_concurrencies` and `request_count`.

```
TOKEN=$(gcloud auth print-access-token)
END=$(date -u +%FT%TZ); START=$(date -u -v-7d +%FT%TZ)
mon() { curl -s -G -H "Authorization: Bearer $TOKEN" "https://monitoring.googleapis.com/v3/projects/${PROJECT}/timeSeries" --data-urlencode "filter=metric.type=\"$1\" AND resource.labels.service_name=\"${SVC}\"" --data-urlencode "interval.startTime=$START" --data-urlencode "interval.endTime=$END" --data-urlencode "aggregation.alignmentPeriod=3600s" --data-urlencode "aggregation.perSeriesAligner=$2" --data-urlencode "aggregation.crossSeriesReducer=$3" --data-urlencode "view=FULL"; }
mon run.googleapis.com/container/billable_instance_time ALIGN_RATE REDUCE_SUM | jq '[.timeSeries[]?.points[]?.value.doubleValue] | {hours: length, mean: (add / length), max: max}'
mon run.googleapis.com/container/memory/utilizations ALIGN_PERCENTILE_99 REDUCE_MAX | jq '[.timeSeries[]?.points[]?.value.doubleValue] | {hours: length, hourly_p99_max: max}'
mon run.googleapis.com/container/max_request_concurrencies ALIGN_PERCENTILE_99 REDUCE_MAX | jq '[.timeSeries[]?.points[]?.value.doubleValue] | {hours: length, hourly_p99_max_concurrent: max}'
mon run.googleapis.com/request_count ALIGN_RATE REDUCE_SUM | jq '[.timeSeries[]?.points[]?.value.doubleValue] | {hours: length, mean_per_s: (add / length), max_per_s: max}'
```

`memory/utilizations` is a fraction of the container's limit (the service's memory is read with `gcloud run services describe $SVC --project $PROJECT --region $REGION --format='value(spec.template.spec.containers[0].resources.limits)'`): **MEASURE** `hourly_p99_max` in MiB = fraction × limit. **It is the largest of the hourly 99th percentiles, not a maximum:** Cloud Run offers no maximum for this metric, so a short spike above it is possible; the rule of section 3 takes it with a margin for that, and the container gets a memory limit after the move whose restarts are watched (a restart count above 0 in the first day is a stop). (A control: `billable_instance_time` must read about 0.99 as the product owner counted; if it does not, the reading is wrong and nothing below is decided on it.)

**2c. The VM's room, on the dev VM now and on the prod VM after the window.** Three samples ten minutes apart in the busy hours (09:00–18:00 KST) and one at 04:00 KST; the figures that matter are what the stack really uses, not what the machine has.

```
gcloud compute ssh sprintable-vm-dev --project $PROJECT --zone asia-northeast3-a --tunnel-through-iap --command "free -m; echo; sudo docker stats --no-stream --format 'table {{.Name}}\t{{.MemUsage}}\t{{.CPUPerc}}'; echo; uptime; vmstat 1 5"
```

**MEASURE** per sample: `available` of `free -m`, the memory each container holds (`db`, `backend`, `frontend`, `caddy`, `gateway-db` on prod), the load average and the idle percentage of `vmstat`. The machine is an e2-medium (4 GiB, [RUNBOOK §4](RUNBOOK.md)); the database has `shared_buffers=256MB` and `max_connections=60`.

## 3. How the numbers decide

| What the log and Monitoring show | Case | What follows |
|---|---|---|
| **All** requests together keep less than 0.1 of an instance busy (the last line of 2a: below 0.1 concurrent on average over 24 hours), but they come at least every 15 minutes all day, and CPU throttling is off | **A. Billing, not a connection** | **Do not move anything yet.** Switch `sprintable-mcp-prod` to request-based CPU (`gcloud run services update sprintable-mcp-prod --project $PROJECT --region $REGION --cpu-throttling`; undo: `--no-cpu-throttling`): an idle instance between short requests is then not billed, so the bill follows the time the requests are really being served. The new monthly figure = the measured active seconds × the request-based rates of the catalog (the product owner reads them), plus the per-request charge; **MEASURE** it after a day. If that is a few dollars, the story is closed without a move, and the VM is spared one more container. Because the figure is an upper bound of the busy share, the **billed seconds** fall to at most a tenth of today's; the bill is not computed from that — the request-based rates are higher per second, and a per-request charge and the start-up and shut-down time are added — it is **read after a day** (**MEASURE**). |
| All requests together keep 0.1 or more but the long ones (over 30 s) keep less than 0.1 (both averages of 2a) | **A′. In between** | Do the switch of case A first (it is one line and undoable) and **measure the bill after a day**; the busy share is then known, not bounded. If the bill is still above the target, the cost is in the short requests themselves and not in a held connection; the move into the VM (section 4) is then the remaining way, decided with that day's bill (question 4). |
| The long requests (`GET` or `POST`, over 30 s) keep 0.1 or more concurrent on average over 7 days | **B. A held connection** | A held request is billed as an active request on either mode of billing, so request-based CPU does not help. Moving the server into the VM is the answer (section 4). First find who holds them (user agent, and whether they come by `mcp.sprintable.ai` or by the `run.app` address): the holders by the Cloudflare name move with a DNS record; the holders of the `run.app` address need the forwarder of step 4c, **and a forwarder that holds the same streams is active all day**: the forwarder of step 4c is on request-based billing (`--cpu-throttling`, 1 vCPU, 256 MiB), where a held request is charged as active time at the catalog's request-based rates, which are not lower per second than the instance-based ones the product owner counted with (one instance with 1 vCPU active all day ≈ 58 USD at those instance-based rates) — **unmeasured**; the product owner reads the request-based rates. A saving only if the holders can be moved. |
| The server's memory (hourly p99 maximum) + the room on the VM | **Fit** | The server fits in the VM if the **lowest** `available` memory of the samples (2c) is at least 1.5 × the server's `hourly_p99_max` + 256 MiB of margin + the largest request body it can be asked to hold (16 MiB, decoded twice at worst: take 48 MiB), **and** the lowest idle percentage of `vmstat` stays above 30. If it does not fit, the alternatives are written with their price before anything is built: a bigger VM class (e2-standard-2: the price of the class is read from the catalog) or case A on Cloud Run. |

The rules of the table are the author's proposal (0.1 because under request-based billing the bill follows the active seconds, which the averages bound from above, so below it the billed seconds fall to at most a tenth of today's — the money is read after the switch, not computed; the factor 1.5 because the memory number is a percentile, not a maximum); the product owner decides them (question 1).

## 4. Design (case B, or case A if it is not enough) — one paragraph

A service `mcp` in `compose.yml`: **the backend's image** (`${BACKEND_IMAGE}`, so a release brings both at the same digest), command `python -m sprintable_mcp`, `MCP_TRANSPORT=http`, `SPRINTABLE_API_URL=http://backend:8000` (the compose network — no turn through the front door and the internet), `MCP_ALLOWED_HOSTS` the one name it is served under, no secret (every request brings its own bearer key; the service sets **no** `AGENT_API_KEY`, so the code's constant placeholder is the fallback — the secret that the Cloud Run service may carry is not copied into the stack, and the removals sheet lists it so that nothing else is left reading it), a memory limit (`mem_limit`) of 1.5 × the measured `hourly_p99_max` + 256 MiB (the same margin as the fit rule: there is no measured maximum, only a percentile), its restarts watched for the first day, `restart: unless-stopped`, `expose: 8080`, a healthcheck on its own port, and `depends_on: backend (healthy)`. The front door gets one more site, `{$MCP_HOST}`, with `reverse_proxy mcp:8080 { flush_interval -1 }` (a stream is sent as it arrives, as for the API), the same filtered logs as the other two sites, and its certificate is Caddy's own; `hosts.mcp` joins `hosts.api`, `.realtime` and `.app` in `env/<environment>.yaml`, and `deployer.py` passes `MCP_HOST` to the Caddy container (a release without the name stops, as for the three others). **The addresses:** (1) the Cloudflare names `dev-mcp` and `mcp` change from a proxied record to the Cloud Run address into a **DNS-only A record to the VM** (a proxy buffers a stream, the reason the other three names are DNS-only): a client that uses the name changes nothing; (2) the `run.app` MCP addresses (`sprintable-mcp-dev-…`, `sprintable-mcp-prod-…`) keep working by the same device as step 4c: one revision of the same service, a Caddy that hands every request to the new name, with its own loop mark, no environment, no secret and an account with no role — built from the same `deploy/vm/forwarder/` (the upstream is a setting of the file, `FORWARD_TO`); (3) when the count of requests that reach the forwarder is zero for the product owner's days, the Cloud Run service goes (a removals sheet of its own, with the way back). **Order:** measure (this file) → decide → `develop` + dev VM (the compose service, the site, the host in `env/dev.yaml`, tests that go red when reverted) → the dev round (an agent lists the tools, calls one and holds a stream through the new name, with the server's own clock) → the security domain reads the key and path exposure → after the prod move and one day: prod.

## Questions for the owner (one line each)

1. Are the rules of section 3 right: case B from 0.1 concurrent long requests, and «fits» = lowest `available` ≥ 1.5 × the server's hourly p99 + 256 MiB + 48 MiB, with idle above 30%?
2. If the numbers say case A is enough, is closing the story with the billing switch (no move) what is wanted?
3. For case B, who moves the holders of the `run.app` address (nobody: the forwarder keeps them, and costs about the same until they move)?
4. In case A′ with the bill still above the target after the switch: move the server into the VM (section 4) or accept the bill?
