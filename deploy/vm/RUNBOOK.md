# RUNBOOK — dev on one VM (story 4796)

Who does what: **gcloud, DNS and anything that changes a running service is the PO's hand** (this runbook gives the exact command and one line to undo it). The agent writes code, runs
tests and reads results. Disruptive steps (§8 DNS switch, §7 database move) are announced to 선생님 by the PO before they are run.

Names used below (dev). Prod is the same with `prod` for `dev` — see §12.

```bash
export PROJECT=sprintable-494803 REGION=asia-northeast3 ZONE=asia-northeast3-a ENV=dev
export VM=sprintable-vm-$ENV DISK=sprintable-data-$ENV IP=sprintable-vm-$ENV-ip SA=sprintable-vm-$ENV
export DEPLOY_BUCKET=sprintable-vm-$ENV-deploy BACKUPS_BUCKET=sprintable-vm-$ENV-backups
```

## 1. Buckets (deploy input, backups)

```bash
gcloud storage buckets create gs://$DEPLOY_BUCKET  --project $PROJECT --location $REGION --uniform-bucket-level-access --public-access-prevention
gcloud storage buckets create gs://$BACKUPS_BUCKET --project $PROJECT --location $REGION --uniform-bucket-level-access --public-access-prevention
cat > /tmp/lifecycle.json <<'EOF'
{"rule":[{"action":{"type":"Delete"},"condition":{"age":14,"matchesPrefix":["db/"]}},{"action":{"type":"Delete"},"condition":{"age":7,"matchesPrefix":["status/"]}}]}
EOF
gcloud storage buckets update gs://$BACKUPS_BUCKET --lifecycle-file=/tmp/lifecycle.json
```
Undo: `gcloud storage rm -r gs://$DEPLOY_BUCKET gs://$BACKUPS_BUCKET` (only while they hold nothing you need).

## 2. VM identity and its access (the part most likely to be forgotten)

The VM's service account stands in for the Cloud Run backend's. **Copy what the backend's service account has** instead of guessing:

```bash
BACKEND_SA=$(gcloud run services describe sprintable-backend-$ENV --region $REGION --format='value(spec.template.spec.serviceAccountName)')
gcloud projects get-iam-policy $PROJECT --flatten='bindings[].members' --filter="bindings.members:serviceAccount:$BACKEND_SA" --format='table(bindings.role)'
gcloud storage buckets list --format='value(name)' | while read b; do gcloud storage buckets get-iam-policy gs://$b --format=json 2>/dev/null | grep -q "$BACKEND_SA" && echo "bucket: $b"; done
```
Send that output to the agent: it is the parity list (Secret Manager accessor **per secret**, Artifact Registry reader, the GCS buckets named in `GCS_*_BUCKET`, Vertex AI/Gemini, Firebase, logging). Secrets are granted one by one (the dev runtime account lost its project-wide accessor in story 4798); the prod list is taken from the prod account's own output, not copied from dev.

```bash
gcloud iam service-accounts create $SA --project $PROJECT --display-name "Sprintable $ENV VM"
SAE=$SA@$PROJECT.iam.gserviceaccount.com
# always (a project-level binding names its condition — the project policy holds a conditional binding, and gcloud then refuses an unconditioned call in a script):
gcloud projects add-iam-policy-binding $PROJECT --member serviceAccount:$SAE --role roles/logging.logWriter --condition=None
gcloud projects add-iam-policy-binding $PROJECT --member serviceAccount:$SAE --role roles/monitoring.metricWriter --condition=None
gcloud projects add-iam-policy-binding $PROJECT --member serviceAccount:$SAE --role roles/artifactregistry.reader --condition=None
gcloud storage buckets add-iam-policy-binding gs://$DEPLOY_BUCKET  --member serviceAccount:$SAE --role roles/storage.objectViewer   # read only: the VM cannot change what it will run
gcloud storage buckets add-iam-policy-binding gs://$BACKUPS_BUCKET --member serviceAccount:$SAE --role roles/storage.objectCreator  # backups + status files: it can ADD objects, never replace or delete them
gcloud storage buckets add-iam-policy-binding gs://$BACKUPS_BUCKET --member serviceAccount:$SAE --role roles/storage.objectViewer   # … and read them back (restore, restore-check)
# per secret the declaration reads (ids such as cron-secret or SUPPORT_GATEWAY_TOKEN_SECRET_dev included) plus the new database password — never project-wide.
# Secrets the VM does not read (the Cloud SQL / pgbouncer connection strings) get no grant:
for S in $(python3 deploy/vm/bin/render_env.py --secret-ids deploy/vm/env/$ENV.yaml); do   # exactly the ids the VM reads (incl. the new DB password), nothing project-wide
  gcloud secrets add-iam-policy-binding $S --project $PROJECT --member serviceAccount:$SAE --role roles/secretmanager.secretAccessor
done
# then the rest of the parity list (PO's output of 2026-10-26, runtime account cloudrun-runtime-dev):
#   project roles: roles/aiplatform.user (dev only — prod has none) · roles/artifactregistry.reader (already above)
#   cloudsql.client is NOT copied: the VM has no Cloud SQL
#   buckets, roles/storage.objectAdmin on each: sprintable-avatars-dev · sprintable-channel-media-dev · sprintable-memo-attachments-dev
#   (the attachments bucket is dev-only — not the bucket dev and prod used to share; story 5269 creates it, so grant after it exists)
for B in sprintable-avatars-dev sprintable-channel-media-dev sprintable-memo-attachments-dev; do
  gcloud storage buckets add-iam-policy-binding gs://$B --member serviceAccount:$SAE --role roles/storage.objectAdmin
done
gcloud projects add-iam-policy-binding $PROJECT --member serviceAccount:$SAE --role roles/aiplatform.user --condition=None
```
Undo: `gcloud iam service-accounts delete $SAE` (removes its bindings with it).

**Accepted limit — one identity on the VM.** The containers can reach the metadata server, because the backend needs it for Vertex AI, Cloud Storage and Firebase exactly as it does on Cloud Run. So an SSRF/RCE in the backend could use the VM service account, which also holds the deploy-time grants (database password secret, read of the backups bucket, create-only write there). Mitigations in place: per-secret grants only, backups bucket create-only (no overwrite/delete), deploy bucket read-only. Splitting the identities would need a second VM and is not part of this story.
Cloud Build's service account additionally needs `roles/storage.objectAdmin` on `gs://$DEPLOY_BUCKET` (the dev bundle build writes the bundle and `candidates/<sha>.json`, §5 — never `desired.json`, which is written by hand in §7 step 6).

## 3. Database password (new, VM only)

```bash
openssl rand -hex 24 | tr -d '\n' | gcloud secrets create DB_PASSWORD_VM_DEV --project $PROJECT --data-file=-
```
Hex only, no line ending (`tr -d '\n'`): the password is placed inside a connection URL and the tooling refuses anything else. (The deployer takes off ONE trailing line ending, because the first dev run showed the unstripped form is easy to create — `openssl` ends its output with one; a value with more than that, or a space, is still refused.) The value is used the first time the database folder is created;
after that, changing the secret does **not** change the database (rotate with `ALTER ROLE` first, then the secret).
Undo: `gcloud secrets delete DB_PASSWORD_VM_DEV`.

**The support gateway database's password (new, VM only — story 4796, §13).** The gateway's database is a second Postgres container with a password of its own, made the same way and granted to the VM account the same way:
```bash
openssl rand -hex 24 | tr -d '\n' | gcloud secrets create SUPPORT_GATEWAY_DB_PASSWORD_VM_DEV --project $PROJECT --data-file=-
gcloud secrets add-iam-policy-binding SUPPORT_GATEWAY_DB_PASSWORD_VM_DEV --project $PROJECT --member serviceAccount:$SAE --role roles/secretmanager.secretAccessor
```
As with the main database, the image applies the password only when it first creates the (empty) data folder: changing the secret later does not change the database (rotate with `ALTER ROLE` first, then the secret). Undo: `gcloud secrets delete SUPPORT_GATEWAY_DB_PASSWORD_VM_DEV`.

## 4. Address, firewall, disk, VM

```bash
gcloud compute addresses create $IP --project $PROJECT --region $REGION
gcloud compute firewall-rules create $VM-web --project $PROJECT --network default --direction INGRESS --allow tcp:80,tcp:443 --target-tags $VM --source-ranges 0.0.0.0/0
# 22 / 3389: allow only Google's IAP range (priority 800 beats the deny at 900), and deny everyone else for THIS VM — the project-wide default-allow rules are cleaned up separately by the PO
gcloud compute firewall-rules create $VM-iap-ssh --project $PROJECT --network default --direction INGRESS --priority 800 --allow tcp:22 --target-tags $VM --source-ranges 35.235.240.0/20
gcloud compute firewall-rules create $VM-deny-admin --project $PROJECT --network default --direction INGRESS --priority 900 --action DENY --rules tcp:22,tcp:3389 --target-tags $VM --source-ranges 0.0.0.0/0
gcloud compute disks create $DISK --project $PROJECT --zone $ZONE --size 30GB --type pd-balanced
gcloud compute resource-policies create snapshot-schedule $VM-daily --project $PROJECT --region $REGION --daily-schedule --start-time 18:00 --max-retention-days 7
gcloud compute disks add-resource-policies $DISK --project $PROJECT --zone $ZONE --resource-policies $VM-daily
gcloud compute instances create $VM --project $PROJECT --zone $ZONE --machine-type e2-medium \
  --image-family debian-12 --image-project debian-cloud --boot-disk-size 20GB --boot-disk-type pd-balanced \
  --disk name=$DISK,device-name=sprintable-data,mode=rw,auto-delete=no \
  --address $IP --tags $VM --service-account $SAE --scopes cloud-platform \
  --shielded-secure-boot --shielded-vtpm --shielded-integrity-monitoring --metadata enable-oslogin=TRUE
```
Open ports are exactly **80 and 443 (everyone)** and **22 from Google's IAP range only** (3389 is not open; the priority-900 deny makes that true for this VM whatever the project-wide default rules say). The application database's port is not published by compose and has no firewall rule. **The one other port** is 5432 of the support gateway's own database server (`gateway-db`, §13): published on the VM's private address only, behind a deny rule for everyone and an allow rule for the gateway's Cloud Run revisions (§13, step 3).
Images that are not ours (`pgvector/pgvector:pg15`, `caddy:2.8.4-alpine`) are pinned by tag only; after the first pull, record their digests (`docker image inspect --format '{{index .RepoDigests 0}}' <image>`) and commit them into `compose.yml` so a rollback is byte-identical (follow-up).
The extra disk and the snapshot schedule are what survive a lost boot disk (RPO ≤ 24 h by snapshot, ≤ 24 h by dump).
Undo: `gcloud compute instances delete $VM --zone $ZONE` · `gcloud compute disks delete $DISK --zone $ZONE` · `gcloud compute addresses delete $IP --region $REGION` · `gcloud compute firewall-rules delete $VM-web $VM-iap-ssh $VM-deny-admin`.

## 5. The bundle of a sha (dev: Cloud Build builds it on every dev deploy)

**Dev.** After the Cloud Run build of a dev deploy has finished, `cloud-build.yml` starts a **second, separate build** (`cloudbuild-vm.yaml`, `gcloud builds submit --async`, tag `vm-bundle`; the workflow run does not wait for it and does not fail if it fails). Its three steps, dev only: `resolve-backend` (digest of `backend:<sha>` from the registry), `build-frontend-vm` (builds and pushes `frontend-vm:<sha>` for amd64 with the Cloud Run build's public values, the baked values checked before the push), `bundle-vm` (`make_bundle.py`, then uploads `gs://$DEPLOY_BUCKET/bundles/<sha>.tgz` and `candidates/<sha>.json` — the `desired.json` that sha would have; the deployer never reads that path). It writes **no** `desired.json`. It is its own build because a step inside the Cloud Run build once took the worker down (build 844cd9a1) — `allowFailure` and step limits do not help against a dead worker. Where to look: `gcloud builds list --filter="tags=vm-bundle"` and `gcloud storage ls gs://$DEPLOY_BUCKET/bundles/ gs://$DEPLOY_BUCKET/candidates/`. A failed build means this sha has no bundle (the next dev deploy makes one).

**By hand** (only if no dev build has produced the sha you need; not on an Apple-silicon Mac). On a machine with the repository at the commit to run:
```bash
SHA=$(git rev-parse HEAD)
BACKEND_IMAGE=<registry>/backend@sha256:…        # the Cloud Build backend image of this sha, by digest
# the VM's frontend image: apps/web/Dockerfile is unchanged, but the API host is baked in at build time, so it is built again with the VM's hosts (needs Docker + python3/PyYAML).
# It is built for linux/amd64 (the VM's architecture). On an Apple-silicon Mac that runs under emulation and takes long (Next.js build, 6 GB heap) — run it in Cloud Shell or on a Linux amd64 machine instead.
# Backend image digest: gcloud artifacts docker images describe asia-northeast3-docker.pkg.dev/$PROJECT/sprintable/backend:$SHA --format='value(image_summary.digest)'   (the sha must be a develop commit whose dev build exists)
# --set values = the public build values of the Cloud Run build of the SAME environment (cloud-build.yml `steps.env`); an empty one is written `NAME=`.
FRONTEND_IMAGE=$(deploy/vm/bin/build-frontend-vm.sh $ENV $SHA <registry>/frontend-vm:$SHA --push \
  --set NEXT_PUBLIC_GA4_MEASUREMENT_ID= --set NEXT_PUBLIC_EE_ENABLED=true --set NEXT_PUBLIC_SUPPORT_WIDGET_ENABLED=true \
  --set NEXT_PUBLIC_SUPPORT_GATEWAY_URL=<the support-gateway URL — a Cloud Run service that stays where it is> --set NEXT_PUBLIC_TOSS_CLIENT_KEY=<dev toss client key> | tail -n1)   # prints <registry>/frontend-vm@sha256:…
python3 deploy/vm/bin/make_bundle.py --sha $SHA --backend-image $BACKEND_IMAGE --frontend-image $FRONTEND_IMAGE --out /tmp/vm-bundle
gcloud storage cp /tmp/vm-bundle/bundles/$SHA.tgz gs://$DEPLOY_BUCKET/bundles/$SHA.tgz     # bundle first …
# … desired.json is put in place in §7 step 1 (the deploy timer stays off until step 6, after the database is restored)
```

## 6. Bootstrap the VM

```bash
# the bundle goes to the VM from the PO's machine (the VM needs no gcloud for this step; bootstrap installs the Google Cloud CLI if the image lacks it):
gcloud storage cp gs://$DEPLOY_BUCKET/bundles/$SHA.tgz /tmp/vm-bundle.tgz
gcloud compute scp /tmp/vm-bundle.tgz $VM:/tmp/ --zone $ZONE --tunnel-through-iap
gcloud compute ssh $VM --zone $ZONE --tunnel-through-iap
# on the VM:
mkdir b && tar -xzf /tmp/vm-bundle.tgz -C b
sudo b/bin/bootstrap.sh dev sprintable-494803 sprintable-vm-dev-deploy sprintable-vm-dev-backups <ops-email>
```
Bootstrap enables only Docker: the deploy, backup and restore-check timers are enabled in §7 step 6, after the database is restored. (A VM bootstrapped by the first version of this script has the backup and restore-check timers on: `sudo systemctl disable --now sprintable-backup.timer sprintable-restore-check.timer` until §7 step 6.)

Re-run it from a newer bundle whenever `deployer.py`, `render_env.py`, the units, `bootstrap.sh` or **`compose.yml`** change (README; the deployer refuses a bundle whose `compose.yml` differs from the copy bootstrap installed).

**Private plain file** — the non-secret values of the live services, per service, readable by root only. Made from the live Cloud Run services (values stay on this machine / that VM; they are not pasted anywhere):
```bash
for SVC in backend frontend; do
  gcloud run services describe sprintable-$SVC-$ENV --region $REGION --format=json \
   | jq --arg s $SVC '{($s): ([.spec.template.spec.containers[0].env[] | select(.value != null) | {(.name): .value}] | add)}'
done | jq -s 'add' > private-plain.json
gcloud compute scp private-plain.json $VM:/tmp/ --zone $ZONE --tunnel-through-iap && rm private-plain.json
# on the VM:  sudo install -m 0600 -o root -g root /tmp/private-plain.json /etc/sprintable/private-plain.json && shred -u /tmp/private-plain.json
```
The deployer reports which names are missing (names only) and refuses a file that group/others can read. Entries the live service holds as secrets are not in the file (they come from Secret Manager).

**Before any cutover — do the live services still have the names this declaration was written from?** (the tests only compare the declaration with the copy; this compares the copy with the service as it is now)
```bash
for SVC in backend frontend; do
  gcloud run services describe sprintable-$SVC-$ENV --region $REGION --format=json \
   | python3 deploy/vm/bin/check_live_names.py deploy/vm/env/live-names.$ENV.txt sprintable-$SVC-$ENV
done   # «ok: N names match» twice; anything else lists added / gone / changed NAMES (never values) — update the declaration first
```

**`JWT_SECRET` is per environment (story 4798 AC6 — done).** Dev reads `JWT_SECRET_DEV` (backend and frontend, as the live dev services do since 2026-10-26 23:52Z); prod's declaration reads `JWT_SECRET_PROD` from the start. The old shared `JWT_SECRET` entry is deleted at 4798 AC9, so **no declaration may read that name** (a test pins it). The IAM loop in §2 grants exactly the ids the declarations read.

## 7. Move the data — **disruptive, announced first**

Writers (users, desktop apps, phones) are stopped for the length of the dump-restore. Measure first (§7a), announce with the measured number.

7a. Rehearsal (no downtime): dump Cloud SQL dev to a file, restore it on the VM with steps 1, 3, 4 and 5 only (not step 2, and **not step 6**: the application and the timers stay off, or the real restore later would find a running backend and refuse), time each step, compare row counts, then **clean up**: the rehearsal dump is a copy of the whole dev database — `sudo find /srv/sprintable/import -name '*-rehearsal-*' -delete` on the VM (`find` does the matching as root; a `sudo rm` with a `*` would be expanded by your own shell, which cannot read the root-only folder) and, from the PO's machine, `gcloud storage rm "gs://$BACKUPS_BUCKET/import/*-rehearsal-*" --project $PROJECT` (double quotes: the variable must expand, the `*` is gcloud's) (the VM account may create objects there, not delete them). The same after the real move and the soak, for the `-final-` files. On a live database the tables written during the rehearsal differ in the row-count diff — expected; the real run (writers stopped, step 2) must give an empty diff. The restore command of step 5 carries `RESTORE_WIPE=yes` (the database may hold the rehearsal data; on an empty database the variable changes nothing).

**The dump is taken on the VM.** Cloud SQL dev has a private address only (no public IP — found on the first rehearsal attempt), so it can not be reached from a laptop; the VM is in the same VPC. The connection URL goes from the PO's machine to the VM on **standard input** of one ssh command and lives in the memory of `dump-source.sh` only (never in an argument list, a file, the history or the output); the VM account gets **no new permission** (it has no access to the database secrets, by design). Undo: nothing to undo — no grant was made.

1. The private address of the source: `gcloud sql instances describe <dev-instance> --project $PROJECT --format=json | jq -r '.ipAddresses[] | select(.type=="PRIVATE") | .ipAddress'` → `$SRC_IP`. The connection secret is `DATABASE_URL_DIRECT_DEV_SPRINTABLE` (the direct URL, not the pooler's); its value is read by the PO's own account.
   Once per VM, before the first dump: put the version to run in place and start only the database — `gcloud storage cp gs://$DEPLOY_BUCKET/candidates/$SHA.json gs://$DEPLOY_BUCKET/desired.json --project $PROJECT` (the sha of a dev build whose steps in §5 succeeded; with a hand-built bundle instead: `gcloud storage cp /tmp/vm-bundle/desired.json gs://$DEPLOY_BUCKET/desired.json --project $PROJECT`; the deploy timer is still off, so nothing deploys), then on the VM `sudo python3 /opt/sprintable/bin/deployer.py --db-only` (it needs a `desired.json` to know the release, and starts the database container and nothing else).
2. Stop writes: close the public door of the Cloud Run dev backend (`--max-instances 0` is not allowed — the minimum is 1) and pause the scheduler jobs that call it.
   `gcloud run services update sprintable-backend-dev --project $PROJECT --region $REGION --ingress internal` — then check from outside: `curl -s -o /dev/null -w '%{http_code}\n' https://<the Cloud Run backend address>/api/v2/health` must NOT print 200.
   **The ingress flag alone does not stop every writer:** Cloud Run's internal ingress also admits traffic from the same project's network (this VM included), and a request already in flight finishes. So (a) if the temporary front door of §7c runs, stop it first (`sudo /opt/sprintable/bin/front-door.sh stop`); (b) the Cloud Run frontend (`sprintable-frontend-dev`) and the hosted MCP (`sprintable-mcp-dev`) are same-project callers of the backend and write through it: close them for the dump too (`gcloud run services update <service> --project $PROJECT --region $REGION --ingress internal`; undo `--ingress all`); (c) wait out the longest request (the backend's request timeout) and then show in the Cloud Run request log that **no request other than the health check** arrived during the last minutes — the scheduler's cron endpoints are GET requests and still write, so «no POST» proves nothing; a non-200 from outside proves only the outside is closed.
   `gcloud scheduler jobs list --project $PROJECT --location $REGION` → `gcloud scheduler jobs pause <job> --project $PROJECT --location $REGION` for each job that targets the backend (note them).
   Undo: `gcloud run services update <service> --project $PROJECT --region $REGION --ingress all` for **each service closed above** (`sprintable-backend-dev`, `sprintable-frontend-dev`, `sprintable-mcp-dev`) and `gcloud scheduler jobs resume <job> --project $PROJECT --location $REGION` for each paused job. After a successful move the hosted MCP is reopened once its backend URL has been changed (§9, §7c); the backend and the frontend stay closed during the soak as the way back.
3. Dump and count **on the VM** (the database container must be up — the `--db-only` of step 1; `dump-source.sh` is installed by bootstrap, or `sudo install -m 0755` it from a bundle into `/opt/sprintable/bin/`):
   `gcloud secrets versions access latest --secret=DATABASE_URL_DIRECT_DEV_SPRINTABLE --project $PROJECT | gcloud compute ssh $VM --project $PROJECT --zone $ZONE --tunnel-through-iap --ssh-flag=-T --command "sudo /opt/sprintable/bin/dump-source.sh --host $SRC_IP --label rehearsal --upload"`
   (`--ssh-flag=-T`: no terminal, so the URL travels on the pipe; the script refuses a terminal on purpose. Use `--label final` for the real run.) It takes the row counts, dumps with a throw-away container of the VM database's own image (same Postgres major), checks the dump lists table data, writes the checksum, and with `--upload` copies dump, checksum and counts to `gs://$BACKUPS_BUCKET/import/` (created only (`--no-clobber`); file names carry the time and the process id, and an existing name is never reused). It prints seconds per step, the size, and the paths under `/srv/sprintable/import/` (`<env>-<label>-<time>-<pid>.dump` · `.dump.sha256` · `.counts.tsv`).
4. Nothing to do: the checksum sidecar and the upload were part of step 3 (`restore.sh` verifies a `gs://` source against the sidecar; a local file on the data disk needs no copy).
5. On the VM, restore from the file step 3 printed (the database container is already up from step 1):
   `sudo env RESTORE_WIPE=yes /opt/sprintable/bin/restore.sh /srv/sprintable/import/<env>-<label>-<time>-<pid>.dump > counts-vm.tsv` and `sudo bash -c 'diff /srv/sprintable/import/<env>-<label>-<time>-<pid>.counts.tsv <(grep -P "^\S+\t\d+$" counts-vm.tsv)'` (the import folder is root-only; `sudo` closes the descriptor a bare `<(…)` would hand over, so the whole line runs under `bash -c`) — **empty diff = row counts equal** (writers stopped; see 7a for a rehearsal). restore.sh prints "restore done in N s".
6. Enable the deployer (`desired.json` is already in place from step 1; to run another version copy its `candidates/<sha>.json` over `desired.json` first) **and the two database timers** (they wait for the restored database — bootstrap leaves them off, a backup run before the restore would fail every night): `sudo systemctl enable --now sprintable-deploy.timer sprintable-backup.timer sprintable-restore-check.timer`. Watch `journalctl -u sprintable-deploy -f` and the newest object under `gs://$BACKUPS_BUCKET/status/dev/`: states go `deploying → deployed` (migrate runs before the swap).

Undo of the move as a whole: nothing was deleted from Cloud SQL — scale Cloud Run back up (step 2 undo) and leave DNS where it is (§8 is a separate step).

## 7c. Dev cutover in three phases — the front door first (PO decision 2026-10-27)

Why: the data move takes minutes, but moving every client (lane agents' MCP, the Electron app's stored addresses, GitHub/Polar/GA4 registrations, the scheduler, the connectors) takes people and days. So the clients move first, to the VM's address, while the VM still hands everything on to Cloud Run; the data move comes last and only flips where the VM hands requests to. In front of `dev-app` / `dev-api` / `dev-mcp` there are Cloudflare Worker routes (`sprintable-dev-app-proxy`, `sprintable-dev-api-proxy`, `sprintable-mcp-dev-proxy`) with `run.app` addresses written into them: changing a record's content does nothing while its route exists — a route has to be deleted (or retargeted) in the same step.

**Phase 1 — `dev-api` to the VM, data still on Cloud SQL (users notice nothing; `dev-app` and `dev-mcp` stay as they are).**
1. Cloudflare, in this order, after writing the old values down (`dns-before-cutover.json`): (a) delete the route `sprintable-dev-api-proxy`; (b) change the record `dev-api` to **A → the VM address, DNS only, TTL 60**; (c) **wait until two public resolvers agree** — `dig +short dev-api.sprintable.ai @1.1.1.1` and `dig +short dev-api.sprintable.ai @8.8.8.8` print only the VM address (no CNAME, no Cloudflare address) — before step 2: the certificate check of the front door otherwise sees the old answer and fails.
2. On the VM, if the rehearsal left the stack up (the front door refuses to start next to the stack's Caddy): `sudo systemctl disable --now sprintable-deploy.timer sprintable-backup.timer sprintable-restore-check.timer`, `sudo systemctl stop sprintable-deploy.service` (a deploy already running could bring the stack's Caddy back for up to its two-hour limit) and `sudo docker stop sprintable-caddy-1 sprintable-backend-1 sprintable-frontend-1`. Then at once: `sudo /opt/sprintable/bin/front-door.sh passthrough --host dev-api.sprintable.ai --upstream https://sprintable-backend-dev-787818285179.asia-northeast3.run.app` (checks the address, validates the Caddyfile, starts one Caddy container; it refuses to run while the stack's own Caddy runs; the certificate is requested now and is stored in the stack's Caddy folder). `sudo /opt/sprintable/bin/front-door.sh status` shows what it points at.

## 8. Lane wheel on the VM, then DNS — **disruptive, announced first**

Before any DNS record moves, the VM is tested by address (hosts file or `curl --resolve`) with the lane wheel: login · conversation · desktop relay · MCP · phone instruction.
**First-VM measurement — which address does the backend count?** (`TRUST_FORWARDED_FOR` is on; the answer must be the real caller, not Caddy and not a forged value.) From a machine outside Google, through the whole path (Caddy → backend, no hop in between):
send more requests than the limit from ONE machine, each with a different, valid forged address in `X-Forwarded-For` (`9.9.0.1` … `9.9.9.150`; an invalid one such as `9.9.9.300` is thrown away by `client_ip()` and the socket address is counted instead, which would spoil the measurement), to a per-IP-limited endpoint **that does nothing**: `POST /api/v2/desktop/setup-codes/exchange` with a code that does not exist (limit 240 per minute per instance, counted by `client_ip`; an unknown code is a read, then `code_not_found` and a rollback — no write, no mail, no outside call; the code is 20+ characters, the verifier 43+ characters of `[A-Za-z0-9._~-]`). Do not use the verification-resend limiter: it sends real mail. **Send more than the limit times the number of instances that can answer** — the counters live in each instance's memory (Cloud Run: instances × 240 pass; the VM runs one instance: exactly 240). The dev backend runs 2 to 8 instances (`backend_min_instances=2`, `backend_max_instances=8` in `cloud-build.yml`) and a burst can scale it up, so send at least 240 × 8 = 1,920, round to 2400, inside one minute (`V=$(printf 'a%.0s' $(seq 1 43)); seq 1 2400 | awk '{printf "9.9.%d.%d\n", int(($1-1)/250), ($1-1)%250+1}' | xargs -P 16 -I{} curl -s -o /dev/null -w '%{http_code}\n' -X POST https://dev-api.sprintable.ai/api/v2/desktop/setup-codes/exchange -H 'content-type: application/json' -H "X-Forwarded-For: {}" -d "{\"code\":\"measurement-no-such-code-0001\",\"verifier\":\"$V\"}" | sort | uniq -c`; the JSON content type is needed: without it the body is not read and the answer is a 422 that the limiter never counts; 300 cannot tell the cases apart when there are two instances — measured in Phase 1: 1000 forged requests gave 480 passed = 2 × 240 and 520 × 429, with the backend at its minimum of 2; 1000 would not have been enough from 5 instances up). Expected: you hit 429 at the limit regardless of the forged values (the limiter counts your real address). If you never reach 429, the forged value is being counted; if a *second* machine is limited at the same moment, a shared (Caddy/private) address is being counted — expected behind the pass-through (Phase 1/2: Cloud Run counts the VM as the caller), **not** on the VM's own backend after Phase 3. Either way stop and tell the agent — do not switch DNS.
Caddy needs the real hostnames to issue certificates; until DNS points at the VM it cannot, so the **first certificate is issued after the record is switched** (a short window with a certificate error is expected; announce it).
For the `app` host behind the Cloudflare proxy: Cloudflare SSL/TLS mode must be **Full (strict)**.

## 11. Day-to-day on the VM

- Status: the newest object under `gs://$BACKUPS_BUCKET/status/dev/` (`gcloud storage ls gs://$BACKUPS_BUCKET/status/dev/ | tail -n1`; one small object per tick, kept 7 days; `state`: up-to-date · deploying · deployed · failed · rolled-back · rollback-failed · skipping-failed).
- **Database connection budget.** The VM database allows `max_connections=60` (`compose.yml`; changing it is a compose change: `bootstrap.sh` again and a database restart), 3 of them reserved for the superuser, so 57 are usable. The backend is one process on direct connections (`DB_PGBOUNCER=false`) and holds, at most: its request pool `DB_POOL_SIZE + DB_MAX_OVERFLOW` (20 + 10 = 30), the worker pool (2 + 1 = 3), and the raw `LISTEN` connection outside the pools (1) — 34. Beside it: the migration at deploy time (2), the backup's `pg_dump` (1), a person's `psql` or the row-count script (2), and room (1) — 6. 34 + 6 = 40 ≤ 57. With a pool of 5 + 5 the first day's lane streams, 26 relays and the frontend exhausted it (`QueuePool limit of size 5 overflow 5 reached, timeout 30`, hundreds of times, relay POSTs answered 502 by Caddy). Raise the pool only inside this budget (25 + 15 still fits: 44 + 6 = 50). To see whether it holds: `sudo docker exec sprintable-db-1 psql -U <user> -d <database> -c "select state, count(*) from pg_stat_activity group by 1"` and count the `QueuePool limit` lines in the backend log. A request that keeps its session for long (not a bigger pool) is the next suspect if errors continue.
- **Changing an `env/<environment>.yaml` value before the next release (temporary, reversible).** The private plain file cannot do it (overrides win over it), and a hand edit of the compose project is overwritten by the next deploy. What works is a rebuilt bundle of the SAME git sha: `gcloud storage cp gs://$DEPLOY_BUCKET/desired.json ./desired.prev.json`; download and unpack the bundle it names; edit the value in `env/<environment>.yaml`; `python3 deploy/vm/bin/make_bundle.py --src <the unpacked folder> --sha <sha> --backend-image <backend_image> --frontend-image <frontend_image> --out /tmp/rebuilt` (both image values from `desired.prev.json`); upload `/tmp/rebuilt/bundles/<sha>.tgz` under another name (`bundles/<sha>-rebuilt.tgz`), set `"bundle"` in `/tmp/rebuilt/desired.json` to that name, upload it as `desired.json`, and let the deploy timer (or `sudo python3 /opt/sprintable/bin/deployer.py`) pick it up. The deployer re-extracts a release folder whose checksum stamp differs, finds nothing to migrate, swaps the backend, checks health and ready, and puts the previous release back if they fail. Undo: `gcloud storage cp ./desired.prev.json gs://$DEPLOY_BUCKET/desired.json`. Put the value into the repository afterwards, or the next normal release brings the old one back.
- A version that failed **before** the swap is retried after 5 minutes; one that failed **after** the swap (and was rolled back) is not retried until `desired.json` changes, or `sudo python3 /opt/sprintable/bin/deployer.py --force` (which also redeploys the version that is already running, e.g. after a rotated secret).
- Roll back by hand: upload the previous `desired.json` (keep the last one: `gcloud storage cp gs://$DEPLOY_BUCKET/desired.json ./desired.prev.json` before a risky release). Migrations are not rolled back — a migration must work with the previous image.
- Backups: daily 03:00 KST → `gs://$BACKUPS_BUCKET/db/` (14 days); weekly `restore-check` prints `restore_seconds=… tables=… rows=…` (`journalctl -u sprintable-restore-check`).
- Secrets: a rotated secret takes effect on the next deploy (`--force` redeploys the same version); the database password has its own rule (§3).
- What the VM trusts: **write access to the deploy bucket = control of the deployment.** Whoever can write it (Cloud Build's service account) decides what runs as root there; only `compose.yml` is pinned to the copy installed on the VM — the `Caddyfile` (front door, certificates) and `env/<environment>.yaml` (which secrets are read, which variables are set) come from the bundle itself. The deployer therefore accepts images only from our own Artifact Registry project, and a `compose.yml` only if it is **exactly** the one `bootstrap.sh` installed on the VM (every key and value of every service, compared as documents) — so a compose change is an infrastructure change: re-run `bootstrap.sh` from the new bundle (§6), a human step; a normal release only changes image digests and `Caddyfile`/`env` files. Keep write access to the deploy bucket to that one service account.
- A migration that already ran is not undone by a rollback; the previous image must work with the new schema (expand first, contract in a later release). Before a risky migration run `sudo systemctl start sprintable-backup.service`.
- The registry login exists only while images are pulled (`docker logout` right after).
- If a swap to a new release succeeded but the run died before `current.json` was written, the next run first puts the previously recorded release back and then deploys the new one again (one extra flip, nothing lost).
- Log scrubbing covers the values read from Secret Manager (and the database password) — not plain values from the private file, split values or re-encoded ones (base64); do not put secrets in the private plain file.
- Docker keeps each container's environment in its own root-only configuration under `/var/lib/docker` (as for any container); only root on the VM can read it, and IAP-only SSH + OS Login decide who is root.

## 13. The support gateway's database on the VM (story 4796, PO decision 2026-10-28: option «다»; AC7 with the security domain's lens)

**Decision.** The gateway receives text from outside people through the widget, so a hole in it must not lead to the VM's service account (the backend's secrets) and the gateway must not hold a long-lived key. Of the options — a container on the VM with the metadata server blocked and a service-account key (a long-lived key), the same with a fake metadata server, a second VM — the PO chose: **the gateway stays on Cloud Run with its own service account (no key, nothing of the VM), and only its database moves to the VM.** The database sits in a **second Postgres container of its own** (`gateway-db`: own data folder, own docker network, `max_connections=30`), published on the VM's **private address**, so the one server that listens to the VPC holds the gateway's data and nothing of the backend — no backend role, database or password can be reached through it, and the backend's containers cannot reach it. The main database's connection budget (§11) is untouched: 34 + 6 = 40 of 57.

**The gateway's connection budget (its own server).** Cloud Run's maximum of 2 instances is **per revision** (10 per service): while a revision is replaced, the old revision's idle instances still hold their pool (3 each) beside the new revision's instances (3 + 2 each) — **overlap worst case 2 × 3 + 2 × 5 = 16 of 27** (30 minus the 3 connections Postgres reserves for its superuser); the migration job adds 1, a second, traffic-less test revision would add more. The application role's own limit is 24. The pipeline carries the pool values **only when they are set** (an empty value means the variable is not sent at all).

**Who can do what (AC7).**
- **The server's superuser** (`gw_admin`) has **no password and no way in over any network address**: the access rules (`gateway-db-pg_hba.conf`, rendered by the deployer from `support_gateway.allow_from` — the default file lets nobody in) allow it the unix socket inside the container only (`docker exec`). The image is started with «trust» only so that no superuser password has to exist; `gateway-db-init.sh` replaces the data folder's own rules by the strict ones at once, so even without the mounted file no network address is trusted.
- **The application's role** (`support_gw`, password in Secret Manager) is an **ordinary role** that owns the gateway's database and nothing else: not a superuser, no program execution on the server, no server files, no settings, no other database (`postgres`, `template1` refuse it twice — by the rules and by the grants). It is made on the first start of the empty data folder only; its password reaches the server through the init script's standard input with statement logging switched off for that session (a slow or failing statement is otherwise written to the server's log with its text). Changing the secret later does not change the database — rotate with `ALTER ROLE` first, then the secret.
- **The server never logs what a statement was run with** (`log_parameter_max_length=0`, `…_on_error=0`): the gateway stores what outside people typed.
- **The metadata server is unreachable from this container**: it has its own bridge `br-gwdb`, and `sprintable-gateway-db-firewall.service` keeps a `DOCKER-USER` rule dropping traffic from that bridge to `169.254.169.254`. The deployer **asks from inside the container** before a release is swapped in and refuses it if the metadata server answers. (IPv6 is off on the VM and in Docker here; if it is ever turned on, the rule needs its twin.)
- **The firewall** (below) lets only the gateway's own Cloud Run revisions reach port 5432.

**This step (the VM side).** A declaration with a `support_gateway` block (`env/dev.yaml`; prod has none yet) brings up `gateway-db` with every release: the deployer reads its password secret and the VM's private address from the metadata server (checked: a private IPv4 address, never «all interfaces», never a public one), creates its data folder, and starts it (compose profile `gateway-db`, healthy before the swap, probed after it). The access rules file is written for a first start (the container needs a file to mount) and otherwise **only inside the swap, after `pending.json` exists** — until then it holds the rules of the release that is running, so a container that starts in the meantime (a reboot, a re-creation) reads those; a crash inside the swap is settled by the next run, which puts the recorded release's rules back. Every path in its compose service is the same in every release (the rules file and the first-start script are copied to `runtime/`), so compose never re-creates it because a release changed. A setting in its environment that changed (a rotated password secret, a new private address) makes compose re-create it when the release is brought up; if that release then fails before the swap, the deployer brings the database back **as the running release has it** (a no-op when nothing was re-created). A deploy **never stops it** — it holds the gateway's data — **except when the metadata server answers from inside it**: then the container is stopped (killed if it will not stop; if even that fails the failure says «COULD NOT BE STOPPED» and the PO stops it by hand; its data folder stays) and the release refused, because a server that can reach the VM's identity must not keep running; the deploy service also **requires** `sprintable-gateway-db-firewall.service`, so no deploy runs while that rule is not in place. **After a boot or a restart of docker** the container is not restarted by docker (its restart policy is «no»): `sprintable-gateway-db-firewall.service` (enabled at boot, restarted with docker) puts the rule in place and only THEN starts it, so there is no moment in which it runs without the rule; the backup and restore-check units are ordered after that unit, and it waits (at most 60 s) until the server answers. `backup.sh` also dumps it (`db-gateway-<env>-….dump`, same bucket folder and lifecycle as the main dumps; a VM whose data folder `gateway-postgres` exists treats a missing container as a failed backup), `restore-check.sh` proves it restores each week, and `restore.sh` takes `DB_SERVICE=gateway-db` (what it restores is owned by the application role; it first **shuts the door** (the role may no longer CONNECT, so nobody new gets in), then **refuses while any session is still open on that database** — the gateway runs on Cloud Run, so open sessions are the only sign that it is still writing — and opens the door again only after the restore finished. **It never drops the gateway's database before the replacement has loaded**: the dump loads into a database beside it (`<name>_restore_<time>`), and the two change names only on success — the old one stays as `<name>_before_restore_<time>` (closed to the gateway) until somebody drops it; if the load fails the old database is untouched and the door is opened again. A restore into an empty database that fails leaves the door shut and prints the one command that opens it). Nothing points at it yet and Cloud Run's gateway keeps using Cloud SQL.

**Order, and what each step interrupts (PO runs steps 2–5; the agent has no gcloud/ssh):**

| # | Step | Interrupts? |
|---|---|---|
| 1 | merge → the dev build writes `candidates/<sha>.json` | nothing |

**Why step 5 belongs to the window of the load.** From step 5 until the gateway's data is loaded into `gateway-db`, the database holds 0 tables. The nightly backup's gateway part then fails with «lists no table data — refusing» (the main dump is uploaded first — only the unit fails) and the weekly restore check finds no gateway dump. That is **expected and loses nothing**; the refusal is what keeps an empty dump from passing as a backup, so it is not loosened — step 5 is taken in the same window as the load instead (the cutover's last check runs the backup by hand and looks for a new `db-gateway-…` dump).

**Step 3 in commands** (`$SAE`, `$VM`, `$REGION`, `$PROJECT` as in §2/§4):
```bash
# the address the gateway's connection URL will carry must not change if the VM is ever recreated
IPI=$(gcloud compute instances describe $VM --zone $ZONE --project $PROJECT --format='value(networkInterfaces[0].networkIP)'); echo "$IPI"
gcloud compute addresses create $VM-internal --project $PROJECT --region $REGION --subnet default --addresses "$IPI"
# the gateway's OWN subnet. Cloud Run's Direct VPC egress cannot be named by a network tag in an ingress firewall rule (it is on Google's list of limits), so the rule names the SUBNET's address range.
# The default network is an auto-mode network: its automatic subnets lie in 10.128.0.0/9, so the new range is placed OUTSIDE it (rules written for those subnets then do not apply to it), and clear of
# every range already in use (`gcloud compute addresses list --global` shows the reserved service-connection range, `gcloud compute networks subnets list --network default` the subnets). A /25 (128 addresses) holds the service's ceiling of 10 instances with room to spare (a service takes about twice the addresses of an instance, kept 20 minutes after a scale-in); Google's minimum is /26.
GWRANGE=$(awk '/allow_from:/{f=1;next} f&&/^ *- /{print $2; exit}' deploy/vm/env/dev.yaml); echo "$GWRANGE"   # the range is written ONCE, as `support_gateway.allow_from` (the deployer reads it); the commands take it from there
# created if it is not there; if it is (dev: made on 2026-10-28), its range must be the declared one
GWCUR=$(gcloud compute networks subnets describe support-gateway-$ENV --region $REGION --project $PROJECT --format='value(ipCidrRange)' 2>/dev/null)
GWOK=no   # set to yes only when the subnet is there with the declared range; the firewall lines below do nothing otherwise, so a STOP really stops
if [ -z "$GWCUR" ]; then gcloud compute networks subnets create support-gateway-$ENV --project $PROJECT --region $REGION --network default --range "$GWRANGE" && GWOK=yes; elif [ "$GWCUR" = "$GWRANGE" ]; then echo "the subnet exists with the declared range"; GWOK=yes; else echo "STOP: the subnet has the range $GWCUR, the declaration says $GWRANGE"; fi
# look first. An earlier version of this step made the allow rule with a network TAG as its source, which never matches Cloud Run traffic: if the list shows an allow rule whose TAGS column is not empty, delete it
# (`gcloud compute firewall-rules delete $VM-gateway-db-allow --project $PROJECT --quiet`) before creating the pair below; a rule that already has the declared range as its RANGES column needs nothing.
[ "$GWOK" = yes ] && gcloud compute firewall-rules list --project $PROJECT --filter="name~$VM-gateway-db" --format='table(name,priority,sourceRanges.list():label=RANGES,sourceTags.list():label=TAGS)'
# the port. A broader allow rule exists separately in the project, so an allow rule alone would narrow nothing:
# deny 5432 to everyone (priority 900, like the admin-port deny of §4) and allow it earlier (priority 800) from the gateway's subnet only
[ "$GWOK" = yes ] && { gcloud compute firewall-rules describe $VM-gateway-db-deny --project $PROJECT > /dev/null 2>&1 && echo "$VM-gateway-db-deny exists (compare it with the list above)" || gcloud compute firewall-rules create $VM-gateway-db-deny  --project $PROJECT --network default --direction INGRESS --priority 900 --action DENY --rules tcp:5432 --target-tags $VM --source-ranges 0.0.0.0/0; }
[ "$GWOK" = yes ] && { gcloud compute firewall-rules describe $VM-gateway-db-allow --project $PROJECT > /dev/null 2>&1 && echo "$VM-gateway-db-allow exists (compare it with the list above)" || gcloud compute firewall-rules create $VM-gateway-db-allow --project $PROJECT --network default --direction INGRESS --priority 800 --action ALLOW --rules tcp:5432 --target-tags $VM --source-ranges "$GWRANGE"; }
```
**Step 3b — the negative control, in commands (the hard condition of step 5).** A throw-away Cloud Run job on the DEFAULT subnet (so outside the gateway's own) that opens ONE connection to the VM's port 5432. It runs as a service account that holds **no role at all**
(the connection needs none; the gateway's own account holds Vertex and database roles it has no business with here), has a name of its own (a leftover or a pre-existing job is never touched), and carries no secret. The program prints
one line, `result <errno> <word>`, and exits **0 REACHED**, **4 REFUSED** (nothing listens, or nothing denies), **3 TIMEOUT** (the packets were dropped), **5 OTHER** (any other error — for example no route at all: a failure of the job's
network, not a proof of the firewall). `$VM`, `$PROJECT`, `$REGION`, `$ZONE`, `$ENV` as in §2/§4.
```bash
GW=support-gateway-$ENV; STAMP=$(date -u +%m%d%H%M%S)$RANDOM          # every name below carries it: nothing that exists is ever reused, so only what this run made is touched
PROBESA_ID=gwdb-probe-$STAMP; PROBESA=$PROBESA_ID@$PROJECT.iam.gserviceaccount.com; PJU=gwdb-probe-untagged-$STAMP
VMIP=$(gcloud compute instances describe $VM --zone $ZONE --project $PROJECT --format='value(networkInterfaces[0].networkIP)')
GWIMG=$(gcloud run services describe $GW --project $PROJECT --region $REGION --format='value(spec.template.spec.containers[0].image)')
PROBE='^@^-c@import errno, socket, sys; s = socket.socket(); s.settimeout(5); r = s.connect_ex((sys.argv[1], 5432)); kind = "REACHED" if r == 0 else "REFUSED" if r == errno.ECONNREFUSED else "TIMEOUT" if r in (errno.EAGAIN, errno.ETIMEDOUT) else "OTHER"; print("result", r, kind); sys.exit({"REACHED": 0, "REFUSED": 4, "TIMEOUT": 3}.get(kind, 5))@'"$VMIP"
[ -n "$VMIP" ] || echo "STOP: no address to probe (VMIP is empty) - nothing is made below"
[ -n "$VMIP" ] && gcloud iam service-accounts create $PROBESA_ID --project $PROJECT --display-name "gateway db firewall probe (no roles)" && SA_MADE=$PROBESA_ID
[ "$SA_MADE" = "$PROBESA_ID" ] && gcloud run jobs create "$PJU" --project $PROJECT --region $REGION --image "$GWIMG" --service-account $PROBESA --network default --subnet default --vpc-egress private-ranges-only --max-retries 0 --task-timeout 60 --command python --args "$PROBE" && JOB_MADE=$PJU
[ "$JOB_MADE" = "$PJU" ] && gcloud run jobs execute "$PJU" --project $PROJECT --region $REGION --wait || true   # failing IS the expected answer; the next lines still run (also under set -e)
[ "$JOB_MADE" = "$PJU" ] && for n in 1 2 3 4 5 6; do gcloud logging read 'resource.type="cloud_run_job" AND resource.labels.job_name="'"$PJU"'"' --project $PROJECT --freshness 15m --limit 20 --format='value(textPayload)' | grep '^result' && break; sleep 10; done
[ "$JOB_MADE" = "$PJU" ] && gcloud run jobs delete "$PJU" --project $PROJECT --region $REGION --quiet
```
**Pass: the log line is `result <n> TIMEOUT`** (the execution failed with `exit(3)`). `gcloud`'s own status after `--wait` only says «failed» — it is not the container's exit code, so the log line is what is read (if it is not there yet, wait a few seconds and read again).
**`REFUSED`: the deny rule is missing — stop** and check the rules above. **`REACHED`: the port is open to a workload outside the gateway's subnet — stop.** **`OTHER`: the job could not reach the network at all — nothing is proven; find out why before step 5.**
The same job created with `--subnet support-gateway-$ENV` instead of `--subnet default` (and its own unique name) is the positive control after step 5 (it must print `REACHED`). When both controls are done: `[ "$SA_MADE" = "$PROBESA_ID" ] && gcloud iam service-accounts delete $PROBESA --project $PROJECT --quiet` (only the account this run created). If a `create` fails the lines after it do nothing, and a leftover job or account of an interrupted run is found by its stamp (`gcloud run jobs list --project $PROJECT --region $REGION --filter='name~gwdb-probe'`; an account whose id is no longer in this shell: `gcloud iam service-accounts list --project $PROJECT --filter='email~gwdb-probe'`, delete it by hand).

The gateway's revisions get their addresses from that subnet through the pipeline change that moves the database (`--subnet support-gateway-$ENV` on its deploy and on its migrate job); until then nothing is allowed — fail closed. Undo: `gcloud compute firewall-rules delete $VM-gateway-db-allow $VM-gateway-db-deny --project $PROJECT` · `gcloud compute networks subnets delete support-gateway-$ENV --region $REGION --project $PROJECT` (only when no Cloud Run revision uses it any more) · `gcloud compute addresses delete $VM-internal --region $REGION --project $PROJECT`.

**This subnet hosts only the gateway service, its migrate job and the throw-away probe job.** Anything else deployed onto it can reach the database's port: no other Cloud Run service or job goes on this subnet. The subnet has Private Google Access **off**, which is fine while the gateway's egress is `private-ranges-only` (calls to Google's APIs do not pass through the VPC); changing it to `all-traffic` later needs NAT or Private Google Access first.

**The firewall is only proven by controls in both directions** — told apart by SUBNET, not by tag. **Negative — before step 5, as its hard condition:** a connection to `<VM private address>:5432` from a Cloud Run workload on the default subnet (a throw-away job) times out. **Positive — after step 5, before any data moves:** the same connection from the gateway's own subnet (a throw-away job on it, or the gateway's own revision) reaches the server. The gateway moves to the subnet by the pipeline change; the default subnet is not allowed, because it also holds other Cloud Run services. Step 3b above has the commands (the cutover sheet repeats them in its step 2).

**Checks after step 5 (on the VM):** the newest status object says `deployed`; `sudo docker ps --filter label=com.docker.compose.service=gateway-db --format '{{.Names}} {{.Status}}'` shows it healthy; `sudo ss -ltnp | grep ':5432'` shows **one** listener on the private address and none on `0.0.0.0`; inside the container: `sudo docker exec sprintable-gateway-db-1 psql -U gw_admin -d support_gateway -Atc "select rolname, rolsuper from pg_roles where rolname in ('gw_admin','support_gw') order by 1"` prints `gw_admin|t` and `support_gw|f`; the role cannot run a program: `sudo docker exec sprintable-gateway-db-1 psql -U gw_admin -d support_gateway -Atc "set role support_gw; copy (select 1) to program 'id'"` is refused (`permission denied to COPY to or from an external program`); the metadata server is out of reach: `sudo docker exec sprintable-gateway-db-1 bash -c 'timeout 3 bash -c "exec 3<>/dev/tcp/169.254.169.254/80"'; echo $?` prints 1 or 124, never 0; no password in the server's log: on the PO's machine `PW=$(gcloud secrets versions access latest --secret=SUPPORT_GATEWAY_DB_PASSWORD_VM_DEV --project $PROJECT)`, then `LOG=$(gcloud compute ssh $VM --project $PROJECT --zone $ZONE --tunnel-through-iap --command "sudo docker logs sprintable-gateway-db-1 2>&1") && [ -n "$LOG" ] && printf '%s' "$LOG" | grep -c -F -- "$PW"` prints `0` (a failed ssh or an empty log prints nothing: that is not a pass) (the value stays in that shell; `unset PW` afterwards). From outside, `nc -z -w 3 <the VM's public address> 5432` fails. Memory: `free -m` before step 5 and after (the PO measured 1.8 of 3.9 GB in use; the new server is expected to add about 100 MB — **unmeasured until this check**).

**Metadata and IPv6.** The rule that keeps the metadata server out of reach is IPv4 only: IPv6 is off on the VM and in docker, and the bridge `br-gwdb` has no IPv6 network. The day either is turned on, the same rule must exist for IPv6 first.

**A first start that was cut short.** The image runs the first-start script only while the data folder is empty. If the container is stopped after the server was initialised but before the script committed, the next start skips the script and the server answers with no application role: the deployer notices (it asks whether the application role owns the database, not only whether the server answers) and refuses the release with «the application role does not own the database». While `gateway-db` holds **no gateway data** (before the load of the cutover) the way out is to start the first start again. **First look, read only** — the server still answers on its socket: `sudo docker exec sprintable-gateway-db-1 psql -U gw_admin -d support_gateway -Atc "select count(*) from pg_stat_user_tables"` must print **0** (if it says the database `support_gateway` does not exist, the first start was cut short before anything could be loaded: also fine); **any other answer, or any other failure, and nothing below is run** — the role missing from a database that holds data is a different problem and is looked at, not wiped. Then, as ONE chain that stops where anything fails: `sudo docker stop sprintable-gateway-db-1 && [ -z "$(sudo docker ps -q --filter name=sprintable-gateway-db-1)" ] && sudo find /srv/sprintable/gateway-postgres -mindepth 1 -delete` (the container's own name, as above: it needs none of the deployer's environment; the data folder is emptied only once the container is confirmed stopped), and deploy again (`deployer --force`). With data in it, do not empty anything.

**Rolling back across this step:** a rollback goes to the previous release and runs `compose up --remove-orphans` with that release's own `compose.yml`. If that release is older than this step, its compose does not define `gateway-db`, so the container is removed (the data folder stays, the server stops serving the gateway and is not backed up until a release with it is deployed again). Within and after this step nothing of the kind happens; once the gateway uses the database, a return to a release from before this step is a deliberate move back, not an automatic rollback.

**Undo of this step:** copy the previous `desired.json` back (a release whose declaration has no block): the container is left running, with its data (a deploy does not stop it); stop and remove it by hand only when the gateway's data is no longer wanted: `sudo docker compose … --profile gateway-db rm -sf gateway-db` and delete `/srv/sprintable/gateway-postgres`.

**No application-layer TLS in dev (accepted by the PO):** traffic inside the VPC is encrypted by Google below the application, but the database does not speak TLS itself. **Required before prod (AC of the story; also item 6 of §12's list):** `ssl=on` for `gateway-db` with a certificate, and `sslmode=require` in the gateway's connection URL.

**Not in this step (the next change):** (1) the pipeline: the gateway's deploy loses `--add-cloudsql-instances`, gets the pool (3 + 2, sent only when set), the subnet `support-gateway-dev`, and the migrate job follows; (2) the cutover sheet: dump of `support_gateway` from Cloud SQL (`dump-source.sh`) → restore into `gateway-db` (`DB_SERVICE=gateway-db restore.sh`, with a row-count diff) → a new version of `SUPPORT_GATEWAY_DATABASE_URL_dev` (the VM's private address, the application role) → redeploy → a widget session, a message, an escalation and a real Vertex call, with the freeze window measured and the two firewall controls above; undo = the old secret version while Cloud SQL exists.
